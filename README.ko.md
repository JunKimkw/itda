# 🕊️ 잇다 (Itda) — 동네 가게와 주민을 잇는 서비스

[English](README.md) | **한국어**

> 사진 한 장으로 동네 가게의 AI 홍보 게시물을 만들고, 모든 가게를 실시간 동네 지도에 띄우고, 직접 가게를 찾아간 주민에게 보상을 주는 모바일 웹앱입니다.

**2026 KW 해커톤**(10조 · 컴미컴)에서 서울 노원구 월계1동을 대상으로 만들었고, 해커톤 전시회(2026년 10월 13일)에서 실시간으로 시연했습니다. 관람객은 포스터의 QR 코드를 찍고 그 자리에서 휴대폰으로 앱을 써 봤습니다.

**🔗 체험하기:** https://itda-kappa.vercel.app (**"베타 테스터로 체험하기"**를 누르면 가입 없이 모든 기능을 써 볼 수 있어요)

## 📖 해결하려는 문제

월계1동의 작은 가게들은 홍보 문구, 카드뉴스, SNS를 운영할 시간도 인력도 부족합니다. 그래서 주민은 신메뉴나 할인 소식을 제때 알기 어렵고, 결국 프랜차이즈로 발길이 향합니다. 잇다는 이 간극을 양쪽에서 좁힙니다.

- **사장님**은 사진과 메뉴판만 올리면 AI가 홍보 게시물을 써 주고, 쿠폰을 발행하고 방문 퀘스트에 참여할 수 있습니다.
- **주민**은 사진 피드와 동네 가게 실시간 지도를 보고, 직접 가게를 찾아가 비둘기를 키우며 쿠폰을 받습니다.
- **접근성**: 모든 가게 프로필에 입구 턱 유무와 엘리베이터 정보를 보여 주고, 큰 글씨와 큰 버튼으로 화면을 구성했습니다.

## 👥 팀과 내 역할

3인 팀: 임아연, **김준영(본인)**, 장서현

저장소 커밋 94개 중 **73개**(약 26,000줄)를 작성했습니다. 맡은 부분은 다음과 같습니다.

- **클라이언트 앱 전체** (React + TypeScript): 손님·사장님 모드, 피드, 지도, 가게 프로필, 퀘스트, 쿠폰, 사장님 센터, AI 게시물 제작 흐름, 관리자 화면
- **백엔드 도메인** (Spring Boot): 가게 등록, 퀘스트, 비둘기 성장과 보상, 쿠폰과 정산, PRO 구독, 게시물 공개·관리, 스크랩, 이벤트, 공지, 의견, 관리자 API, API 명세
- **인프라**: AWS EC2 서버, API 프록시를 둔 Vercel 호스팅, GitHub Actions 자동 배포, 운영 DB 마이그레이션
- 아래에서 설명할 **전시회용 베타 모드**

팀원 장서현은 백엔드 기반(JWT 회원가입·로그인, 가게 목록 API, 공통 응답 형식)과 **AI 생성 파이프라인**(Amazon Bedrock 이미지 생성, Polly TTS, FFmpeg, OCR, S3)을 만들었습니다.

## ✨ 주요 기능

**주민**
- 인스타그램처럼 넘겨 보는 가게 사진 피드 (PRO 가게 우선 노출, 스크랩, 공유)
- 카카오맵 동네 지도: 업종별 핀, 쿠폰 배지, 퀘스트 가게 깃발, 가게 영업시간을 읽어 거르는 "영업 중만" 필터
- 가게에서 **GPS + 매일 바뀌는 QR 코드**로 방문을 인증하는 퀘스트, 방문할 때마다 비둘기 먹이 지급
- 비둘기 키우기: 레벨업할 때마다 사장님들이 보상으로 내놓은 쿠폰을 뽑음

**사장님**
- 음식·메뉴판 사진으로 AI 홍보 게시물 제작 (게시물당 사장님 사진 최대 4장)
- 쿠폰 발행, 계산대에서 코드로 사용 처리, 월별 정산
- 유료 퀘스트 가게 등록으로 손님 방문 유도, PRO 구독으로 피드 우선 노출과 게시물 재수정

**운영자**
- 관리자 화면: 가입자, 가게, 쿠폰, 보상 풀, 베타 의견, 공지 관리
- 앱 안 이벤트·공지 게시판과 초기 사장님 이벤트 (보상 쿠폰을 처음 내놓은 선착순 10곳에 PRO와 퀘스트 가게 30일 무료)

## 🔧 내가 해결한 문제

**서버 없이 앱 전체를 돌리는 베타 모드**
전시회에서는 관람객이 가입 없이 몇 초 만에 모든 기능을 써 볼 수 있어야 했고, 운영 DB에 테스트 데이터가 쌓여서도 안 됐습니다. 저는 이미 실제 API의 규칙과 에러 코드를 그대로 따르는 브라우저 목업 API(`localStorage` 저장)를 만들어 두었습니다. "베타 테스터" 스위치 하나로 모든 기능을 이 목업으로 돌리고, 관람객을 체험용 사장님 계정으로 로그인시켜 휴대폰 한 대로 손님과 사장님을 모두 체험할 수 있게 했습니다. 그 결과 QR을 찍은 사람이 아무리 많아도 전시회 동안 서버에는 요청이 거의 가지 않았습니다.

**공정한 보상 구조와 빈 보상 풀 대비**
레벨업 보상은 사장님들이 내놓은 쿠폰에서 나옵니다. 추첨은 **남은 수량에 비례**해서, 쿠폰을 30장 내놓은 가게는 10장 내놓은 가게보다 뽑힐 확률이 3배 높습니다. 출시 직후에는 쿠폰을 내놓은 가게가 하나도 없었기 때문에, 보상 풀이 비면 서버가 **3주짜리 교환권**을 대신 줍니다. 바꿀 쿠폰이 생기면 배지로 알려 주고, 교환권이 만료되면 비둘기 먹이 4개로 바뀝니다. 서버와 목업이 같은 추첨 방식을 써서 베타 모드도 실제 서비스와 똑같이 동작합니다.

**1GB 서버 살리기**
운영 서버는 AWS t2.micro(RAM 1GB, 디스크 8GB)였습니다. 메모리가 부족해 OS까지 멈추면서 회원가입이 안 되는 일이 있었습니다. 스왑 2GB를 추가하고, Java 힙 크기를 제한하고, 앱을 systemd로 옮겨 꺼지면 스스로 다시 켜지게 했습니다. 이후 옛 jar 백업으로 디스크가 가득 차 배포 업로드가 실패하자, 배포할 때 백업을 하나만 남기고 남은 공간이 700MB보다 적으면 미리 멈추도록 했습니다.

**자동 롤백이 있는 CI/CD**
`dev`에 push하면 jar를 빌드하고, **EC2 Instance Connect**의 임시 키로 서버에 접속합니다. 그래서 GitHub에 SSH 키를 저장하지 않습니다. 이어서 jar를 올리고 서비스를 재시작한 뒤 정상적으로 켜지는지 기다리고, **새 버전이 켜지지 않으면 이전 jar로 되돌립니다**. 클라이언트는 별도 워크플로가 Vercel에 배포합니다.

**운영 중에 찾은 작은 버그들**
- 휴대폰에서 사진을 올리면 "서버에 연결할 수 없어요"라는 엉뚱한 오류가 났습니다. 원인은 Vercel 함수의 요청 본문 4.5MB 제한이었습니다. 이제 올리기 전에 브라우저에서 사진을 줄이고, 413 응답이 오면 알기 쉬운 안내를 보여 줍니다.
- 관리자가 사장님 기능을 시험하려면 테스트 가게가 필요했지만, 실제 손님에게 보여서는 안 됐습니다. 관리자가 등록한 가게는 지도, 피드, 보상 풀에서 숨기고, 초기 사장님 이벤트 자리도 차지하지 않게 했습니다.

## 💡 배운 점

- 단 하루 전시회라도 실제 사용자에게 내놓으면 로컬에서는 겪지 못한 문제가 드러납니다: 메모리, 디스크, 요청 크기 제한, 메일 계정 잠금.
- 실제 명세를 따르는 목업 API에 일찍 투자한 것이 두 번 도움이 됐습니다. 서버를 기다리지 않고 화면을 만들 수 있었고, 나중에는 그대로 전시회 베타 모드가 됐습니다.
- 혼자 운영을 책임질 때는 스왑, 자동 재시작, 롤백, 디스크 확인 같은 작은 안전장치가 생각보다 훨씬 중요합니다.
